Lesson 0007 · G2

在线推送，离线补拉

本课的唯一目标：把“连接在线”与“通知送达”分开建模，让在线用户收到推送，离线用户以后仍能补拉未读消息。

G2 目标：在线推送、断线期间的未读标记或补拉，以及多实例下消息如何到达目标连接。本课先完成单机内存版本；持久化和跨实例路由留到后续课程。

本课独立示例：examples/0007-push-notifications-and-replay。

1. 先分清三个动作

动作含义当前示例
发布（publish）业务系统产生一条面向用户的通知。HTTP POST 创建通知。
推送（push）用户在线时通过 WebSocket 发送给当前连接。服务端直接写入 session。
补拉（replay）用户不在线时，重新连接后读取尚未确认的通知。HTTP GET 未读列表，再 ACK。

WebSocket 只解决实时连接，不自动提供离线存储、消息确认或重放。把这三件事混成“发送成功”，会让断线期间的消息丢失。

2. 源码导读：发布路径与连接状态

POST /api/users/{userId}/notifications
    ↓
NotificationController.publish
    ↓
NotificationService.publish
    ├─ onlineUsers 有连接 → session.sendMessage
    └─ 无连接/发送失败 → unread[userId].add

WebSocket connect/close
    ├─ connect    → onlineUsers.put(userId, session)
    └─ disconnect → onlineUsers.remove(userId, session)

NotificationService 的核心不变量是：在线索引只代表当前连接，不代表通知已经被用户业务确认；未读列表保存的是尚未 ACK 的通知。

Handler 只维护连接生命周期，Controller 负责补拉和确认。分开这两个入口，能看清 WebSocket 和 HTTP 在可靠通知中的不同职责。

3. 可靠性取舍

  • 写入 WebSocket 成功，不等于用户已经看到或处理通知。
  • 在线发送失败时，应把通知转入补拉路径，而不是静默丢弃。
  • ACK 需要幂等：重复 ACK 应该得到稳定结果，不应重新产生副作用。
  • 生产环境通常使用数据库或消息系统保存通知，并用唯一 ID、序列号或幂等键处理重复和重试。

4. 运行和验证

cd examples/0007-push-notifications-and-replay
mvn test
mvn spring-boot:run
  1. 建立 ws://localhost:8080/ws/notifications?alice 连接。
  2. POST 一条通知，确认浏览器立即收到。
  3. 关闭连接，再 POST 一条通知。
  4. GET 未读列表，确认离线通知存在。
  5. POST ACK，确认该通知从未读列表移除。

5. 失败案例

现象根因方向
断线期间通知消失只实现了 WebSocket 发送，没有持久化或未读补拉。
同一通知重复处理重连重放没有唯一 ID 或客户端幂等处理。
发送异常后仍认为已送达没有把写失败转入离线队列，或状态更新和发送没有明确顺序。
多实例中通知发给错误节点在线连接只在本机内存，发布请求没有经过共享路由或连接目录。

6. 练习：先回忆，再验证

运行示例后回答下面 4 个问题：

  1. 为什么 WebSocket 写入成功不等于通知已经被用户处理？
    查看答案

    写入成功只说明服务端把数据交给当前连接，无法证明客户端收到、展示或完成业务处理。需要客户端确认、唯一 ID 和补拉机制才能表达更强的可靠性。

  2. 为什么在线索引和未读列表必须分开？
    查看答案

    在线索引描述当前连接在哪里；未读列表描述哪些通知还没有被确认。连接会变化，但未确认的业务事实不能因为连接断开就消失。

  3. 为什么通知需要唯一 ID？
    查看答案

    重连、重试和补拉可能让同一通知被发送多次。唯一 ID 允许客户端和服务端做去重、ACK 和幂等处理。

  4. 多实例部署时，为什么单机内存的 onlineUsers 不够？
    查看答案

    用户连接可能在实例 A，而发布请求到达实例 B。实例 B 看不到 A 的内存索引，需要共享消息通道、连接目录或让消息经过能路由到目标连接的组件。
