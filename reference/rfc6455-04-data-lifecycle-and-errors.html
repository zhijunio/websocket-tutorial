RFC 6455 §6-§8：数据收发、关闭与错误

本篇把连接建立后的运行时行为补完整：如何发送和接收一条消息，如何完成 Closing Handshake，如何区分正常关闭、异常断开和协议失败，以及为什么重连必须使用退避。

状态主线：OPEN 可以交换数据；发送或收到 Close 后进入 CLOSING；底层 TCP 关闭后进入 CLOSED。没有收到 Close 就断开时，应用通常看到的是异常关闭语义，而不是一个可在线发送的 1006。

1. §6.1 发送数据

RFC 的发送算法从一个前提开始：连接必须处于 OPEN。如果发送过程中连接状态发生变化，发送方必须中止剩余步骤。

  1. 确认 WebSocket 连接处于 OPEN。
  2. 把数据封装成一个 WebSocket 帧，或在数据很大/尚未完整生成时封装成多个分片帧。
  3. 第一帧使用 Text 或 Binary opcode。
  4. 最后一帧设置 FIN=1。
  5. 如果由客户端发送，所有帧都必须掩码。
  6. 如果协商了扩展，按扩展定义处理额外数据和语义。
  7. 把形成的帧写入底层网络连接。

这条规则的工程含义是：业务层的“发送消息”不能绕过 WebSocket 帧编码器直接写字符串或 JSON 到 TCP。框架会替你完成编码，但发送前仍要处理连接状态、发送顺序、队列上限和慢客户端。

2. §6.2 接收数据

接收方从底层连接读取字节，并必须按 §5.2 解析为 WebSocket 帧：

TCP 字节流
    ↓
帧解析：FIN / RSV / opcode / MASK / length / payload
    ├── 控制帧：Close / Ping / Pong，立即按 §5.5 处理
    └── 数据帧：Text / Binary，按 FIN 和 Continuation 重组
    ↓
完整 WebSocket Message
    ↓
业务处理器：JSON / STOMP / 自定义协议
输入接收动作应用可见结果
未分片数据帧读取 opcode 和 Application data。立即形成一条完整消息。
分片首帧记录消息类型，等待 Continuation。暂时不应当作完整业务消息。
Continuation按发送顺序拼接 Application data。直到最后一帧 FIN=1 才形成完整消息。
控制帧按 Close/Ping/Pong 规则处理，可插入分片消息之间。不改变正在重组的数据消息边界。

扩展可以改变 Payload 的解释、消息边界或 Application data 的内容，所以通用中间件只有在理解已协商扩展时，才可以安全地改写或合并帧。

3. §7.1 关闭状态机

CONNECTING ── 握手通过 ──→ OPEN
                                │
                   发送或收到 Close
                                ↓
                           CLOSING
                                │
                       TCP 连接已关闭
                                ↓
                           CLOSED
状态/事件RFC 语义实现动作
OPEN可以发送和接收数据。允许业务消息，维护连接和发送队列。
发送 CloseClosing Handshake 开始，进入 CLOSING。停止发送新的数据帧。
收到 Close如果此前没有发送 Close，必须回复 Close。尽快回复并停止新的业务发送。
双方收发 Close应关闭底层 TCP 连接。释放连接、定时器、队列和业务索引。
TCP 已关闭进入 CLOSED；关闭握手完成才算 cleanly closed。触发最终清理和重连判定。

Close 帧交换和 TCP 关闭是两个相关但不同的动作：Close 表示 WebSocket 协议层的意图；TCP FIN/RST 表示传输层连接结束。异常断网时可能只看到后者。

4. §7.1.2-§7.1.7 关闭、失败与清理

4.1 正常关闭

开始 Closing Handshake 时发送一个 Close 控制帧，可包含状态码和 UTF-8 reason。发送方收到对端 Close 后，应关闭底层连接。应用在发送 Close 后不能再发送数据帧。

4.2 Fail the WebSocket Connection

当 RFC 要求连接失败时，客户端必须关闭底层连接；服务端也必须关闭连接，并且应该记录问题。如果连接已经建立，端点通常应先发送合适的 Close 帧，再关闭 TCP；但如果对端很可能无法处理 Close，例如严重协议错误或攻击场景，可以直接关闭。

失败后不能继续处理来自对端的数据，也不能继续尝试响应后续 Close。服务端日志应记录协议错误、连接标识、方向和 close code，但不能记录敏感 Token。

4.3 Close code 的来源

RFC 定义的“连接关闭码”是应用收到的第一个 Close 帧中的状态码。双方几乎同时关闭时，两端看到的关闭码可能不同，因为各自先收到的 Close 帧可能来自不同方向。

代码含义是否可放进 Close 帧
1000正常关闭。可以
1001Going Away，例如服务端下线或页面离开。可以
1002协议错误。可以
1003收到无法接受的数据类型。可以
1005表示没有收到状态码。不能发送，仅供本地表示
1006异常关闭，没有完成 Close 帧交换。不能发送，仅供本地表示
1007消息数据不符合类型要求，例如无效 UTF-8。可以
1008违反策略的消息。可以
1009消息过大，无法处理。可以
1010客户端期望的扩展没有被服务端协商。客户端可以发送
1011服务端遇到阻止其完成请求的意外条件。服务端可以发送
1015TLS 握手失败的本地表示。不能发送，仅供本地表示

扩展、框架和应用可以使用 3000-3999；应用之间约定的私有状态码使用 4000-4999。这些代码的具体语义不是 RFC 6455 自动定义的，必须写进消息协议和故障手册。

5. §7.2 异常关闭与重连

异常关闭可能来自网络瞬断、代理超时、服务端崩溃、TLS 问题、协议错误或资源限制。RFC 明确警告：如果所有客户端在同一时间立即、持续重连，恢复过程会变成对服务端的拒绝服务压力。

5.1 推荐的重连策略

  1. 先判断关闭原因是否值得重连：认证失败、授权拒绝和协议错误通常不能盲目重试。
  2. 第一次重连加入随机延迟；RFC 给出的合理示例是 0 到 5 秒之间随机选择。
  3. 后续失败使用逐步增加的延迟，例如截断二进制指数退避。
  4. 加入最大重试次数、最大延迟、抖动和手动恢复入口。
  5. 重连成功后恢复订阅、房间和离线消息游标，但不要重复创建旧连接的定时器。
delay = min(maxDelay, baseDelay * 2^attempt) + randomJitter

RFC 6455 建议使用退避，但没有规定具体的最大延迟、重试次数或业务恢复语义。序列号、补拉、幂等和订阅恢复属于应用层设计。

6. §8 错误处理与 UTF-8

当端点需要把字节流解释为 UTF-8，却发现字节流不是合法 UTF-8 时，必须使 WebSocket 连接失败。这条规则同时适用于握手期间和后续数据交换。

错误典型处理可能 close code
客户端到服务端帧未掩码服务端关闭连接，可发送协议错误。1002
未知 opcode 或非法帧停止继续解析并失败连接。1002
文本消息无效 UTF-8失败连接，不把损坏文本交给业务层。1007
消息超过实现限制拒绝或关闭，保护内存和队列。1009
策略拒绝拒绝不允许的业务消息或来源。1008

框架可能把协议错误转换为异常、回调或日志；应用应确认这些事件最终会清理会话状态，而不是只记录异常后留下房间成员、订阅或发送队列。

8. 排查断线的顺序

  1. 确认是否曾经收到过 101；如果没有，回到 §3-§4 的握手排查。
  2. 查看 close code、close reason，以及是客户端、服务端还是代理先关闭。
  3. 如果是 1006 或没有 Close，检查网络、TLS、代理 idle timeout、进程崩溃和心跳。
  4. 如果是 1002，检查帧头、掩码、opcode、RSV、长度和分片状态。
  5. 如果是 1007/1009/1008，检查编码、消息大小、授权和业务策略。
  6. 最后检查重连是否有退避、抖动、上限，以及连接清理是否幂等。
