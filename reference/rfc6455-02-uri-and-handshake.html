RFC 6455 §3-§4：URI 与 Opening Handshake

本篇把一个 WebSocket 连接从 URI 解析到 OPEN 状态的完整过程拆开：先确定 host、port、resource name 和 secure flag，再建立 TCP/TLS 连接，发送 HTTP Upgrade，最后校验服务端的 101 响应。

核心判断：只有服务端返回 101 Switching Protocols，并且响应头通过客户端校验后，连接才进入 OPEN。返回 200、401、403、404 或 426 时，仍处于 HTTP 握手处理阶段。

1. §3 WebSocket URI

RFC 6455 定义两个 URI scheme：

ws-URI  = "ws:"  "//" host [ ":" port ] path [ "?" query ]
wss-URI = "wss:" "//" host [ ":" port ] path [ "?" query ]
URI含义默认端口安全属性
ws://普通 WebSocket80不提供 TLS 传输保护
wss://通过 TLS 保护的 WebSocket443secure flag 为 true

1.1 Resource name 如何得到

握手中的 Request-URI 需要对应 URI 的 resource name。构造规则很简单：

  • path 为空时使用 /；否则使用 path。
  • query 非空时，在 path 后追加 ? 和 query。
  • URI fragment 没有 WebSocket 协议语义，不能用于 WebSocket URI。
WebSocket URI握手中的 Request-URI
ws://example.com/chat/chat
ws://example.com/chat?room=blue/chat?room=blue
ws://example.com/

这解释了一个常见的 404：浏览器连接的是 /chat，但服务端实际注册的是 /ws。握手还没有进入业务消息处理，应该先检查 URI、路由和 endpoint 映射。

2. §4.1 客户端建立连接

RFC 把客户端建立连接所需的信息抽象为：

host + port + resource name + secure flag
        + protocols + extensions
        + origin（浏览器客户端）

2.1 连接建立顺序

  1. 解析并验证 WebSocket URI。
  2. 确定目标 host 和 port；如配置了代理，先连接代理。
  3. 如果是 wss://，先完成 TLS 握手和证书校验，并使用 SNI。
  4. 发送 HTTP/1.1 或更高版本的 GET Upgrade 请求。
  5. 等待并校验服务端响应；在响应到达前不能发送后续 WebSocket 数据。

代理场景下，客户端可能先发送：

CONNECT example.com:443 HTTP/1.1
Host: example.com:443

代理建立隧道后，客户端才在隧道中进行 TLS 和 WebSocket Opening Handshake。代理的 CONNECT、TLS 和 WebSocket Upgrade 是三个不同的阶段，不应混为一个“握手失败”。

2.2 客户端请求的强制字段

字段RFC 要求排错意义
请求行必须是 GET，HTTP 版本至少 1.1。不是普通 POST 或 HTTP/1.0 请求。
Host必须包含目标 host；非默认端口时可带端口。影响虚拟主机和网关路由。
Upgrade值必须包含大小写不敏感的 websocket。缺失时可能被当作普通 HTTP。
Connection值必须包含大小写不敏感的 Upgrade token。代理可能丢失 hop-by-hop 头。
Sec-WebSocket-Key每次连接生成；随机 16 字节后 Base64 编码。不是 Token，不是登录凭证。
Origin浏览器客户端必须发送。服务端可据此执行来源校验。
Sec-WebSocket-VersionRFC 6455 的值必须是 13。不支持时服务端可返回 426 和支持版本。

2.3 Key 的真实含义

Sec-WebSocket-Key 是一个 16 字节随机值的 Base64 表示。例如原始字节为：

01 02 03 04 05 06 07 08 09 0a 0b 0c 0d 0e 0f 10

对应的 Header 值是：

Sec-WebSocket-Key: AQIDBAUGBwgJCgsMDQ4PEC==

服务端计算 Accept 时使用的是这个 Base64 字符串本身，不是先 Base64 解码后的 16 字节：

Accept = Base64(SHA-1(Key 字符串
                       + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))

Key 的作用是让服务端证明自己确实理解 WebSocket 握手，而不是复用某个普通 HTTP 响应。它不能替代 Cookie、Authorization、Token 或授权判断。

2.4 可选的子协议、扩展和其他字段

字段客户端表达什么服务端应该怎么回应
Sec-WebSocket-Protocol按偏好顺序列出希望使用的应用层子协议，例如 STOMP。最多选择一个，并且必须来自客户端请求列表；不接受时不要返回该字段。
Sec-WebSocket-Extensions请求协议级扩展，例如 permessage-deflate。只能返回客户端请求过、且服务端实际同意使用的扩展。
Cookie、Authorization 等携带应用认证或会话信息。按对应 HTTP 规范和应用策略处理。

客户端和服务端都必须防止“协商结果越权”：服务端不能凭空声明客户端没有请求的子协议或扩展；客户端发现服务端返回了未请求的内容时，必须使连接失败。

3. §4.2 服务端读取和处理握手

RFC 把负载均衡器和反向代理也视为服务端基础设施的一部分：从第一个终止 TCP 的设备，到真正处理 WebSocket 帧的应用，都属于这条连接的服务端路径。

3.1 服务端读取客户端请求

服务端至少要解析以下内容：

  1. HTTP/1.1 或更高版本的 GET 和 resource name。
  2. Host、Upgrade: websocket 和 Connection: Upgrade。
  3. Base64 解码后长度为 16 字节的 Sec-WebSocket-Key。
  4. Sec-WebSocket-Version: 13。
  5. 可选的 Origin、子协议、扩展、Cookie 和认证字段。

HTTP Header 的顺序不重要。如果握手不符合语法或必要字段缺失，服务端必须停止处理并返回适当的 HTTP 错误，例如 400 Bad Request。这时还没有建立 WebSocket 连接。

3.2 服务端接受前的决策

检查可能结果说明
TLS握手失败则关闭连接wss:// 必须先完成 TLS。
身份认证401 + WWW-AuthenticateRFC 允许服务端在协议升级前执行 HTTP 认证。
重定向3xxRFC 允许服务端重定向，但客户端不被要求自动跟随。
Origin拒绝时通常返回 403Origin 校验是跨站来源策略，不等于用户身份认证。
版本426 Upgrade Required + 支持版本客户端版本不被服务端理解时使用。
资源名称404 Not Found请求的 WebSocket 服务不存在。

4. §4.2.2 服务端响应

接受连接时，服务端必须返回一个有效的 HTTP 响应：

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

[可选] Sec-WebSocket-Protocol: chat
[可选] Sec-WebSocket-Extensions: permessage-deflate
响应条件客户端行为
状态码不是 101按普通 HTTP 响应处理；例如 401 可进入认证流程。
缺少或错误的 UpgradeFail the WebSocket Connection。
缺少或错误的 ConnectionFail the WebSocket Connection。
Accept 与 Key 计算结果不一致Fail the WebSocket Connection。
服务端返回未请求的扩展或子协议Fail the WebSocket Connection。
全部校验通过连接进入 OPEN，可以交换 WebSocket 数据。

4.1 Accept 示例

RFC 使用以下示例：

Key:
dGhlIHNhbXBsZSBub25jZQ==

Key + GUID:
dGhlIHNhbXBsZSBub25jZQ==258EAFA5-E914-47DA-95CA-C5AB0DC85B11

Accept:
s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

这里的 SHA-1 不是用来提供密码学保密性；它只是 WebSocket 握手确认算法的一部分。连接机密性仍由 TLS 提供。
