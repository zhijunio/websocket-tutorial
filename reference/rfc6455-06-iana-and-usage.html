RFC 6455 §11-§14：注册表、复用与规范边界

最后四节不像前面的握手和帧那样直接规定运行时步骤，但它们解释了 WebSocket 如何进入互联网协议生态：哪些名字由 IANA 统一登记、其他规范如何复用 WebSocket，以及 RFC 中哪些内容是规范要求、哪些内容只是历史与参考资料。

先抓住结论：§11 是“命名和分配规则”，不是一次连接的握手流程；§12 是“如何在其他规范中调用 WebSocket 能力”；§13 是作者和参与者致谢；§14 列出 RFC 依赖的规范性和信息性参考文献。

1. §11 IANA Considerations：把协议名称变成公共契约

IANA 注册表的作用，是防止不同规范或实现重复占用同一个协议名字、版本号、关闭码、opcode 或 RSV 位。注册表解决的是跨实现的命名协调问题；它不会替应用完成认证、路由、压缩或消息投递。

1.1 URI scheme：ws 与 wss

Scheme语义工程含义
ws://使用 WebSocket 打开连接。底层连接不由 URI 要求使用 TLS；生产环境通常需要评估明文风险。
wss://使用 TLS 保护的 WebSocket。提供 TLS 的机密性、完整性和端点认证；不自动完成业务授权。

两种 URI 都由 authority、path 和可选 query 组成。path 与 query 会成为发给服务端的 resource name，用于在同一个 Host 和端口上区分服务。也就是说，/chat?room=blue 不是“只是前端字符串”，它参与了连接目标的识别；但其中的 query 是否承载身份票据，属于应用安全设计。

1.2 Upgrade token 与握手 Header

RFC 将 WebSocket 注册为 HTTP Upgrade token，并登记了握手用的 Sec-WebSocket-* Header。这些登记让协议参与者共享稳定的字段名和职责：

字段方向登记所表达的职责
Sec-WebSocket-Key客户端 → 服务端参与服务端生成 Accept，帮助确认这是一次有效的 WebSocket 握手；不是用户认证。
Sec-WebSocket-Accept服务端 → 客户端确认服务端愿意建立 WebSocket 连接；不是授权凭证。
Sec-WebSocket-Extensions双向协商请求并确认连接使用的协议扩展。
Sec-WebSocket-Protocol双向协商选择连接上的应用层子协议，例如某个 STOMP 变体。
Sec-WebSocket-Version请求为客户端，失败响应可由服务端返回协商协议版本；版本号更高不自动意味着向后兼容。

一个很实用的排错边界是：看到 Header 被注册，并不表示框架一定已正确实现它。仍要观察线上握手请求和响应，检查字段出现次数、值和协商结果是否符合 RFC。

2. §11.4–§11.9：扩展、子协议和编号空间

注册表解决什么冲突本课程中的对应物
Extension Name扩展名称、定义文档和已知不兼容关系。permessage-deflate 等握手扩展。
Subprotocol Name应用层子协议标识和定义文档。STOMP over WebSocket；业务协议也应有清晰版本和契约。
Version NumberWebSocket 协议版本号。RFC 6455 使用版本 13。
Close Code关闭原因编号及其唯一语义。1000、1002、1008、1009 和应用自定义范围。
Opcode帧类型编号。文本 1、二进制 2、Close 8、Ping 9、Pong 10。
Framing Header BitsRSV1、RSV2、RSV3 的扩展分配。扩展启用前不能擅自把 RSV 位当成业务标志。

关闭码尤其容易被误用：3000–3999 可用于库、框架和应用并登记；4000–4999 是私有使用范围。范围可用不等于语义已定义。项目仍必须在消息协议、README、日志和测试中写清“哪个代码表示什么，以及客户端是否应该重连”。

3. §12：其他规范如何复用 WebSocket

RFC 6455 把 WebSocket 设计成一个可供其他规范调用的通用双向传输机制。上层规范不必重新发明 TCP 连接、握手、帧和关闭，而是提供连接参数并调用 RFC 定义的算法。

上层规范提供：
  destination = host + port
  resource name
  secure = true / false
  origin
  optional subprotocol

RFC 6455 负责：
  Establish WebSocket Connection
  Send a WebSocket Message
  A WebSocket Message Has Been Received
  Close the WebSocket Connection

这正是“裸 WebSocket”和 STOMP 的关系：STOMP 定义 CONNECT、SUBSCRIBE、SEND、MESSAGE 等应用层语义；WebSocket 负责把这些字节可靠地承载在一条双向连接上。MQTT、私有 JSON 协议或其他规范也可以采用相同的分层方式，但它们不能因此改变 WebSocket 帧的基本规则。

3.1 三个必须分开的概念

概念回答的问题例子
WebSocket 协议字节如何握手、分帧、关闭和报告协议错误？101、masking、Ping/Pong、Close。
WebSocket 子协议连接建立后，Payload 代表什么命令和消息？STOMP、项目自定义 JSON 协议。
WebSocket 扩展是否改变帧或消息的解释、压缩或处理方式？permessage-deflate。

因此，Sec-WebSocket-Protocol 和 Sec-WebSocket-Extensions 不能混为一谈：前者选择应用层协议，后者扩展 WebSocket 的解释机制。Spring 的 STOMP 配置、浏览器的子协议参数和容器的压缩配置，分别落在不同层次。

4. 用 §12 设计一个新 WebSocket 应用

  1. 先定义 resource name，例如 /chat，不要把所有业务语义塞进 URI。
  2. 决定是否使用 TLS；面向真实用户的连接通常使用 wss://。
  3. 决定是否需要子协议。简单回显可以裸 WebSocket；需要订阅、目的地和确认时再评估 STOMP。
  4. 定义消息格式、版本、大小上限、错误语义、顺序、幂等和重连恢复。
  5. 只在确实需要压缩或其他帧级能力时启用扩展，并验证 CPU、内存和延迟代价。
  6. 把 RFC 层、框架层、代理层和业务层的故障指标分开记录。

5. §13：致谢的阅读价值

§13 列出协议演进中参与设计、审阅和讨论的人。它不是实现规则，也不会改变任何握手或帧行为。对学习者而言，它提醒我们：WebSocket 是在 WHATWG、IETF HYBI 工作组和多个领域审阅中逐步形成的协议，规范中的安全、分帧和互操作性要求有明确的工程背景，而不是某个框架的偶然约定。

6. §14：规范性参考与信息性参考

类别含义阅读方式
Normative References理解或实现 RFC 6455 要遵守的基础规范。遇到 URI、HTTP、TLS、UTF-8、Origin、Base64、ABNF 等细节时回查。
Informative References帮助理解背景、已知问题、历史讨论或相关 API，但不是 RFC 6455 的直接实现契约。用于理解轮询、浏览器 API、Cookie 和安全背景，不把它们的每句话都当成 WebSocket 帧规则。

本课程最常回查的依赖包括：HTTP/1.1、URI 通用语法、TLS、UTF-8、随机性、Origin、HTTP Header 注册和 Base64。若某个问题涉及“浏览器 API 怎么表现”，应同时看浏览器 API 文档；若涉及“Spring 如何配置”，应看 Spring 官方文档，而不是把 RFC 当成框架手册。

7. 从 RFC 6455 全文得到的排错地图

没有 101？       → §3–§4：URI、HTTP Upgrade、版本、Key、Origin、代理
101 后不能通信？ → §5–§6：帧头、masking、opcode、分片、扩展、发送/接收
连接突然关闭？   → §7–§8：Close、TCP/TLS、UTF-8、状态码、重连退避
压缩或子协议异常？→ §9、§11、§12：协商结果、注册名称、上层协议边界
安全或资源风险？ → §10：Origin、认证、TLS、限制、非法数据和日志

这张地图的价值在于先定位层次，再选择工具。DevTools 适合看握手和浏览器事件；抓包适合看真实 Header、帧和关闭；应用日志适合看鉴权、房间、队列和业务错误；指标适合看连接数、延迟、积压和重连风暴。
