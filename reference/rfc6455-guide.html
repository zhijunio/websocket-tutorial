RFC 6455：WebSocket 协议导读

RFC 6455 是 WebSocket 的核心协议规范。它规定握手、帧、掩码、控制帧、关闭、扩展和安全边界；它不规定 Spring、Tomcat 或业务消息如何实现。

阅读目标：看到一条 WebSocket 请求或一段帧数据时，能回到 RFC 的对应章节，判断协议行为是否正确，并区分标准要求与框架、代理和业务系统行为。

1. RFC 6455 是什么

项目内容
标题The WebSocket Protocol
发布组织IETF
发布时间2011 年 12 月
作者Ian Fette、Alexey Melnikov
类别Standards Track
协议基础Opening Handshake + TCP 上的 WebSocket 帧

RFC 摘要把 WebSocket 描述为：让受控环境中的不可信客户端代码与远端主机进行双向通信，并使用浏览器常见的 Origin 安全模型。它的目标是减少依赖 XMLHttpRequest、iframe 或长轮询建立多个 HTTP 连接的需要。

2. 协议整体模型

浏览器 / WebSocket 客户端
        │
        │  HTTP Opening Handshake
        │  Upgrade: websocket
        │  101 Switching Protocols
        ▼
同一条 TCP 连接上的 WebSocket 协议
        │
        ├── 数据帧：Text / Binary / Continuation
        ├── 控制帧：Ping / Pong / Close
        └── 可选扩展和应用层子协议：例如 permessage-deflate、STOMP

握手成功后，连接不再按普通 HTTP 的“请求—响应”模型处理。客户端和服务端都可以主动发送 WebSocket 消息；具体的业务语义仍由应用层协议决定。

4. Opening Handshake

GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
字段协议职责不能把它当成什么
Upgrade / Connection声明并确认 HTTP 协议升级。不是业务消息。
Sec-WebSocket-Key客户端为本次握手生成的随机挑战值。不是登录凭证，也不是授权结果。
Sec-WebSocket-Accept服务端根据 Key 和固定 GUID 计算出的握手确认值。不是用户身份认证。
101 Switching Protocols表示 HTTP 层协议切换成功。200 不能替代它。

Accept 的计算规则是：

Base64(SHA-1(Sec-WebSocket-Key +
               "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))

服务端还需要按 RFC 检查请求方法、HTTP 版本、Host、Upgrade、Connection、版本和 Key 等条件。应用层鉴权则应通过 Cookie、Authorization、短期票据或其他明确机制完成。

5. 数据帧和控制帧

RFC 6455 把 WebSocket 数据组织为帧。一个业务消息可能由一个帧组成，也可能因为分片由多个帧组成。

  • FIN：是否是消息的最后一帧。
  • opcode：文本、二进制、Continuation、Close、Ping 或 Pong。
  • MASK：客户端发往服务端的帧必须掩码，服务端发往客户端的帧不应掩码。
  • Payload length：Payload 长度，较长内容使用扩展长度字段。
  • 控制帧不能分片，Payload 长度不能超过 125 字节。

掩码是协议要求的异或变换，不是加密，也不是认证。需要保密性和完整性时，应使用 TLS，即 wss://。

6. 关闭和安全

正常关闭通常包含 Close 帧的交换；异常断网、进程崩溃或代理超时可能来不及完成关闭握手，所以服务端仍必须根据底层断开、超时和心跳结果清理会话。

主题RFC 关注点工程实现还要补充什么
Origin浏览器来源信息和跨站请求风险。允许来源列表、环境配置和拒绝日志。
认证客户端身份认证是应用设计问题。Cookie/Token 验证、过期、授权和最小权限。
TLSwss:// 提供连接保密性和完整性。证书、终止位置、代理转发和内部链路策略。
资源限制实现可以设置消息、连接等限制。有界队列、背压、限流、超时和监控。

7. RFC 与实现的边界

层次主要职责
RFC 6455握手、帧、掩码、控制帧、关闭、扩展和协议错误。
浏览器 WebSocket APInew WebSocket()、send()、事件和 readyState。
Spring/Tomcat/Jakarta端点注册、连接回调、消息处理和容器实现。
Nginx/网关Upgrade 转发、TLS、idle timeout 和连接路由。
业务系统房间、广播、鉴权、离线消息、幂等、多实例路由和背压。

排错时先问“违反了哪一层的契约”：101 之前优先看握手和代理；101 之后再看帧、生命周期和业务协议。不能用 Spring 注解行为替代 RFC 对线上的实际判断。
