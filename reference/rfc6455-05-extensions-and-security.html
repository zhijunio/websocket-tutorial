RFC 6455 §9-§10：扩展与安全

本篇解析 WebSocket 如何协商协议扩展，以及 RFC 6455 对 Origin、非浏览器客户端、掩码、资源限制、认证、TLS 和非法数据的安全要求。

边界：扩展和安全能力必须显式协商或由应用实现。WebSocket 握手成功不等于用户已认证，掩码也不等于加密；真正的传输机密性和完整性来自 TLS，即 wss://。

1. §9 扩展是什么

WebSocket 基础帧格式预留了 RSV 位、扩展数据区域和部分 opcode，允许未来协议扩展增加能力。客户端可以请求扩展，服务端可以接受其中一个或多个；RFC 6455 本身没有定义具体扩展，具体扩展需要由其他规范单独定义。

常见例子是 permessage-deflate，它不是 RFC 6455 §9 直接定义的内容，而是通过握手中的 Sec-WebSocket-Extensions 协商压缩能力。扩展可能改变 Payload 的解释、帧处理顺序或消息边界，因此中间件不能在不了解扩展语义时随意合并或拆分帧。

2. §9.1 扩展协商

2.1 握手中的表达方式

客户端：
Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits

服务端：
Sec-WebSocket-Extensions: permessage-deflate
规则含义
客户端可以请求请求表示“我愿意使用”，不表示扩展已经生效。
服务端只能选择已请求扩展服务端不能凭空返回客户端没有请求的扩展。
客户端收到未请求扩展必须失败避免双方对帧语义产生分歧。
参数必须由扩展规范定义不能任意解释或接受未知参数。
格式错误必须立即失败不符合 ABNF 的协商数据不能继续使用。

2.2 扩展顺序是有意义的

客户端请求列表通常表达偏好顺序；服务端响应列表表达实际启用的扩展顺序。若多个扩展都会修改数据或帧，处理顺序按服务端响应顺序解释。

服务端响应：foo, bar

处理结果：bar(foo(data))

因此，扩展顺序不是装饰性文本。压缩、加密包装、复用或其他帧变换叠加时，客户端和服务端必须遵循对应扩展的定义，否则会出现“握手成功但消息无法解析”的故障。

3. 扩展与 Spring/Tomcat 的边界

层次负责什么排错问题
客户端握手通过 Header 请求扩展。浏览器是否发送了 Sec-WebSocket-Extensions？
服务端握手选择并返回实际启用的扩展。响应是否返回了未请求的扩展？
容器/框架根据协商结果编码和解码帧。框架配置是否和抓包中的协商结果一致？
业务层处理解压后的文本或二进制消息。不要把压缩 Payload 当作普通 JSON。

4. §10.1 非浏览器客户端

RFC 的 Origin 安全模型主要针对“恶意 JavaScript 在可信浏览器中运行”的场景。非浏览器客户端可以伪造 Origin，因此服务端不能仅凭 Origin Header 断言请求一定来自浏览器页面。

无论客户端类型如何，服务端都必须把输入视为不可信：

  • 校验 JSON、命令、房间名、用户标识和消息大小。
  • 不要把消息直接拼进 SQL、Shell、日志或 HTML。
  • 使用参数化查询、输出编码和明确的授权检查。
  • 不要把“握手来自允许 Origin”当成业务授权结论。

5. §10.2 Origin 校验

如果服务端只希望接受特定网站的浏览器脚本连接，应校验 Origin。不接受时，RFC 建议在握手阶段返回 403 Forbidden。

浏览器请求：
Origin: https://app.example.com

服务端策略：
https://app.example.com   允许
https://admin.example.com 允许
https://evil.example       拒绝 403
Origin 校验能解决什么Origin 校验不能解决什么
限制可信浏览器中的恶意脚本滥用连接权限。不能证明用户身份。
作为浏览器来源策略的一部分。不能替代 Cookie/Token 认证。
在握手前拒绝不允许来源。不能替代每个业务操作的授权。

生产实现还要考虑反向代理是否正确转发 Origin、允许列表是否按环境配置，以及日志中是否记录了拒绝原因但没有泄露凭证。

6. §10.3 掩码防护的真实目的

RFC 设计客户端掩码，主要是防止攻击者控制的浏览器脚本把客户端发出的字节伪装成某些 HTTP 请求，从而诱导错误实现的代理缓存或处理这些数据，造成基础设施污染。

客户端必须为每个帧选择新的、不可预测的掩码 key。一个 key 不能被应用预测，下一个 key 也不能由前一个 key 推导；帧开始发送后，正在发送的 Payload 也不能被应用动态改写。

机制主要目的不是它的目的
Client-to-server masking降低恶意脚本控制线上字节形态、攻击中间基础设施的能力。不是加密、不是完整性校验、不是身份认证。
TLS / wss://提供传输机密性和完整性。不自动完成用户授权和业务鉴权。

7. §10.4 实现限制与拒绝服务

攻击者可以发送一个极大的帧，也可以发送大量小帧组成一个很长的分片消息，试图耗尽接收端内存。RFC 要求实现保护自己，并建议同时限制：

  • 单帧 Payload 大小。
  • 重组后的完整消息大小。
  • 单连接发送队列和接收队列。
  • 连接总数、订阅数量和房间成员数量。
  • 消息处理时间、心跳超时和慢客户端积压。

限制触发时可以根据上下文使用 1009（消息过大）、1008（策略拒绝）或直接关闭。具体阈值属于部署和业务设计，应通过指标和负载实验验证。

8. §10.5 客户端认证

RFC 6455 不规定唯一的认证方式。服务端可以使用普通 HTTP 服务已经支持的机制，例如：

机制实现关注点
Cookie会话有效期、CSRF/Origin、跨域策略和代理转发。
Authorization握手前验证、Token 过期、日志脱敏和权限映射。
短期查询参数票据短时有效、一次性使用、避免出现在访问日志和 Referer。
TLS 客户端认证证书生命周期、终止位置和用户身份映射。

Sec-WebSocket-Key、Sec-WebSocket-Accept 和 Origin 都不能单独承担用户身份认证与授权。

9. §10.6 机密性与完整性

RFC 要求 WebSocket 实现支持 TLS，并建议通信时使用 TLS。使用 wss:// 时，TLS 握手保护后续 WebSocket 握手和帧；但 TLS 的安全收益仍取决于密码套件、证书校验、终止位置和内部链路配置。

浏览器 ── TLS + WebSocket ──→ 入口代理 ──?──→ 应用

需要明确：
- TLS 在哪里终止？
- 代理到应用的链路是否仍需加密？
- Origin、认证和授权在哪一层执行？
- 日志和指标是否记录了 Token 或消息正文？

10. §10.7 非法数据

客户端和服务端都必须验证输入。无法理解或不符合安全标准的数据可以直接丢弃 TCP；如果非法数据发生在握手完成后，通常应先发送合适的 Close code，再关闭连接。握手阶段则应返回合适的 HTTP 状态码。

输入问题推荐处理
错误的 path 或 Origin握手阶段返回 HTTP 错误，例如 403 或 404。
非法 opcode、RSV 或掩码协议错误，使用 1002 或直接失败连接。
无效文本编码使用 1007，不能把无效文本交给业务层。
消息超出限制使用 1009 或策略拒绝，并释放已有缓冲。
业务字段不合法验证、授权、限流；必要时使用 1008。

11. §10.8 握手中的 SHA-1

RFC 明确说明，WebSocket 握手使用 SHA-1 不依赖 SHA-1 的碰撞抗性或第二原像抗性。它用于根据客户端 Key 生成握手确认值，不是密码哈希、数字签名或数据完整性保护。

因此，不能因为握手使用 SHA-1 就把它等同于“WebSocket 使用了不安全的密码算法”；也不能因此把握手 Accept 当成认证凭证。连接保密性和完整性仍由 TLS 负责。

12. 一张安全检查表

  1. 是否只允许明确的 Origin，且非浏览器客户端不能靠伪造 Origin 获得额外信任？
  2. 是否在握手或连接建立后完成身份认证，并在每个业务动作上做授权？
  3. 是否使用 wss://，并检查证书、TLS 终止和内部链路？
  4. 是否限制单帧、完整消息、连接数、队列和订阅数量？
  5. 是否校验 JSON、文本编码、命令、房间、用户 ID 和消息大小？
  6. 是否对协议错误、策略拒绝、慢客户端和异常重连建立指标与日志？
  7. 日志中是否不会出现 Cookie、Authorization、Token 或敏感消息正文？
自测：为什么 Origin 校验不能替代 Token 鉴权？为什么掩码不能替代 TLS？请分别从“保护对象”和“攻击模型”回答。
